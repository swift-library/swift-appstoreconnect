# Codegen

## Scope / Purpose

This document defines the package-owned code generation boundary for public App
Store Connect API bindings.

## Context / Boundaries

`AppStoreConnectPublicAPI` is the stable public API module. Trait-gated names
such as `PublicAPICommerce`, `PublicAPIReports`, and `PublicAPIFull` describe
API capability slices, not user-facing SwiftPM products or architectural
targets. Code generation does not define web-session acquisition, private Iris
API calls, workflow orchestration, or CLI behavior.

This document records the package-owned generation strategy.

## Adopted Route

The public API binding route is schema-backed, Apple-generator-first, and
build-derived. The package generation layer is an adapter around the official
OpenAPI toolchain rather than an alternate public API emitter.

The package-owned responsibilities are:

- keep a repository-tracked public API schema snapshot with provenance metadata;
- keep deterministic audit, partition, trait, and generation manifests;
- materialize active OpenAPI input documents from operation, tag, path, and
  schema selectors whenever a typed slice is needed;
- use Apple's `swift-openapi-generator` for typed `types` and `client` output;
- use Apple's `typeOverrides` mechanism only when a trait slice intentionally
  replaces named component schemas with a JSON value fallback;
- generate package-owned capability facades over Apple generated clients;
- run generation through a SwiftPM build tool plugin during ordinary
  `swift build` and `swift test`;
- write generated Swift into SwiftPM's plugin work directory;
- do not commit generated Swift under
  `Sources/AppStoreConnectPublicAPI/Generated`.

The first Apple-only route does not attach a package-owned full-schema catalog
or descriptor emitter to the build. Full-schema lightweight catalog generation
is deferred until the Apple filter/typeOverrides route is proven insufficient
for a specific CLI or SDK workflow.

The SwiftPM targets are:

- `AppStoreConnectOpenAPIGen`: build tool plugin attached to the public API
  generation lane. It reads generation manifests, derives active API slices
  from SwiftPM trait-backed compilation conditions, verifies the locked schema
  inputs, and invokes the package adapter and official generator executables;
- `AppStoreConnectPublicAPIGen`: executable generation adapter used by the
  plugin and diagnostics commands. It dispatches package generation modes to
  active OpenAPI filtering and package facade generation;
- `AppStoreConnectPublicAPIGenCore`: testable manifest, audit, partition,
  reporting, and facade logic shared by the executable and generator tests;
- `Vendor/AppStoreConnectOpenAPI/`: schema snapshot directory with a
  lock/provenance file, audit file, and trait partition manifests.

The selected typed-client lane emits Apple generated `Components`,
`Operations`, `APIProtocol`, and `Client` source for the current public
workflow seed. Optional domain/full API slices use the same Apple generator with
different trait-aligned active OpenAPI inputs and optional JSON value replacement
policies. The plugin generates one active union schema for the current trait set
so one
`AppStoreConnectPublicAPI` module does not receive duplicate `Components`,
`Operations`, `APIProtocol`, or `Client` symbols. The facade lane emits
`AppStoreConnectPublicClient` and capability subclients over the enabled Apple
generated client.

The whole build-plugin toolchain lives under `Plugins/` so the directory
semantics stay aligned. SwiftPM target type still separates plugin glue,
executable tool, and testable generator logic:

```text
Plugins/
  AppStoreConnectOpenAPIGen/
  AppStoreConnectPublicAPIGen/
  AppStoreConnectPublicAPIGenCore/
```

## Schema Snapshot Layout

The schema snapshot is tracked as package input, not downloaded at build time:

```text
Vendor/
  AppStoreConnectOpenAPI/
    spec.lock.json
    schema-audit.json
    README.md
    partitions/
      public-api-traits.json
    schema/
      app-store-connect-openapi.json
```

`spec.lock.json` must record the source URL or repository, exact snapshot
identity, retrieval date, checksum when available, and the normalization command
used before generation. The schema snapshot can be refreshed only through an
explicit review of the official specification.

`schema-audit.json` must be derived from the locked schema and regenerated by
the package generator. It records the OpenAPI version, API title, API version,
path count, operation count, schema count, upload-related construct count,
unsupported construct count, and normalization delta. It is a deterministic
guardrail for reviewing schema changes before generated endpoint coverage
expands.

The snapshot must be selected from the official public API schema source
used for an explicit comparison. Comparison artifacts may inform the decision,
but they are not schema authority for generated source.

## Build Tool Inputs / Outputs

The build tool plugin declares the locked schema, lock file, audit file,
partition manifest, API-slice generation manifests, and Apple generator
configuration as inputs. It writes only generated files and stamps into the
plugin work directory.

The stable `AppStoreConnectPublicAPI` module has a base typed generation
manifest:

```text
Sources/AppStoreConnectPublicAPI/
  openapi-capabilities.json
  openapi-generation.json
  openapi-generator-config.yaml
```

Optional API slices are described as slice manifests, not as public module
names:

```text
Sources/AppStoreConnectPublicAPI/
  OpenAPISlices/
    release.openapi-generation.json
    testflight.openapi-generation.json
    metadata-media.openapi-generation.json
    commerce.openapi-generation.json
    reports.openapi-generation.json
    signing-access.openapi-generation.json
    cloud.openapi-generation.json
    game-center.openapi-generation.json
    distribution.openapi-generation.json
    full.openapi-generation.json
```

Slice manifests describe selection intent. They do not contain hand-trimmed
OpenAPI documents. Each slice manifest records:

- the SwiftPM trait and generated compilation condition that activate the
  slice;
- the slice generation depth, currently `typed`;
- official OpenAPI selectors: operation IDs, tags, paths, and any explicit
  additional schemas;
- the Apple generator config and optional `typeOverrides` policy.

The plugin maps SwiftPM traits to compilation conditions in `Package.swift` and
reads those conditions from `SwiftSourceModuleTarget.compilationConditions`.
For example, `PublicAPICommerce` maps to `ASC_PUBLIC_API_COMMERCE`. The plugin
then selects the matching slice manifests, merges their official selectors,
produces a temporary active OpenAPI document, and passes that document to
Apple's generator. The active input writer follows the same selector model as
Apple's documented filter support and keeps `$ref` closure, schema validation,
and empty-enum normalization deterministic for this package.
Slice manifests may combine tag prefixes with explicit operation IDs when
Apple tags a required relationship operation under a broader owner tag. For
example, `PublicAPIDistribution` selects `apps_webhooks_getToManyRelated`
explicitly because the app-scoped webhook list operation is tagged `Apps`,
while the rest of the webhook operations are selected by the `Webhook` prefix.

The plugin writes verification stamps before generation:

```text
<plugin-work-directory>/
  AppStoreConnectOpenAPISelection.stamp
  AppStoreConnectOpenAPI.active.json
```

`openapi-capabilities.json` records the current base capability groups and
operation IDs. `openapi-generation.json` and slice manifests record the package
adapter mode, API slice, trait, generated compilation condition, filter source,
Apple generator config, and whether `typeOverrides` should replace selected
named component schemas with `OpenAPIRuntime.OpenAPIValueContainer`.

Typed OpenAPI inputs are produced from the locked schema and active API-slice
manifests. A tracked `openapi.json` may exist during the transition, but the
stable contract is the locked full schema plus generation manifests, not a
hand-maintained selected schema file.

The plugin writes selected generated Swift into the plugin work directory:

```text
<plugin-work-directory>/
  GeneratedSources/
    Types.swift
    Client.swift
    Server.swift
    AppStoreConnectPublicAPI+Facade.swift
```

`AppStoreConnectPublicAPI+Facade.swift` is package-owned generated source. It
is derived from `openapi-capabilities.json` plus the active OpenAPI input, wraps
the generated `APIProtocol`, and remains build-derived rather than checked in.

## Generator Commands

The package generator exposes deterministic commands for two audiences:

- `plan`: read the schema snapshot and generation manifests, then print active
  traits, API slices, filters, Apple mode, type override policy, and expected
  file inventories;
- `validate`: run `plan` plus schema provenance, partition, trait, and
  output-path validation;
- `filter-openapi`: resolve active trait compilation conditions, merge slice
  manifests, and write or inspect a deterministic temporary OpenAPI slice plus
  count stamp;
- `verify-openapi-selection`: verify a generated or tracked selected OpenAPI
  input against the locked schema and capability manifest, then write a build
  stamp;
- `generate-openapi-facade`: plugin-facing command that emits package-owned
  capability clients over the generated selected OpenAPI client;
- `generate-type-overrides-config`: diagnostic command that creates an Apple
  generator config replacing selected named component schemas with
  `OpenAPIRuntime.OpenAPIValueContainer`.

The build tool plugin invokes `filter-openapi`, then runs Apple's
`swift-openapi-generator generate` executable with the filtered document and
generator config. Both executables and the selector's core dependency declare
development-host platform conditions; they execute on the host when the public
libraries compile for another platform. The generator's `--plugin-source build` option produces all declared
outputs, including an empty file for each unselected mode. The plugin emits the
facade from the same active OpenAPI input. These commands use only tracked
schema, lock, audit, partition, generation manifests, capability manifest,
generated compilation conditions,
and generator config inputs. A normal build must not require a developer-local
dependency checkout beyond the resolved package graph or network access.

## Planning Model

`plan` should produce a stable inventory for the active generation run:

- schema source pointer and checksum;
- generation mode: `typed`, `facade`, or `filterOnly`;
- enabled traits and API slices;
- Apple filter source: operation IDs, tags, paths, and additional schemas;
- Apple generator modes: `types`, `client`, or both;
- generated output relative paths;
- expected operation, path, and component schema counts;
- type override policy.

The generator should fail before emission when two schema entries map to the
same output path.

## Apple Mapping Policy

The package does not define a parallel schema-to-Swift mapping for typed public
API clients. Typed request and response mapping follows Apple's
`swift-openapi-generator`.

Package-owned mapping policy is limited to:

- generating Apple filter configs from trait partitions and active slice
  manifests;
- applying deterministic schema normalization only when a locked schema artifact
  would otherwise make Apple generated Swift invalid, such as unsupported empty
  enum artifacts;
- applying `typeOverrides` when a trait slice explicitly chooses JSON value
  replacement for named component schemas;
- validating generated operation/path/schema counts against the locked schema
  and partition manifest.

## Generated Source Shape

Generated Swift should preserve public API schema identity at the wire boundary
while keeping local Swift ergonomics explicit:

- generated model names stay schema-shaped unless a compatibility wrapper is
  intentionally handwritten;
- endpoint request/response types remain reachable through
  `AppStoreConnectPublicAPI`;
- generated capability facades expose package-owned subclient names while
  returning generated `Operations.*.Output` values;
- shared transport, retry, pagination, upload, and authentication primitives
  remain in `AppStoreConnectCore`;
- handwritten convenience clients wrap generated payloads instead of replacing
  the generated source of truth;
- unsupported or unstable schema coverage should first be represented through
  Apple filtered generated clients before it becomes a stable
  handwritten API.

## Trait-Aligned Generation

SwiftPM traits control which public API capability slices are compiled into the
package build. The package does not expose a domain slice as a separate
user-facing product or architectural target.

Default traits:

- `PublicAPIBase`: selected deep typed client for current CLI/Workflow/facade
  operations.

Opt-in traits:

- `PublicAPICommerce`, `PublicAPIReports`, `PublicAPIGameCenter`, and similar
  domain traits: Apple filtered deep typed API slices for a capability domain;
- `PublicAPIFull`: aggregate opt-in trait for full public API coverage. It
  means full typed coverage for the active official schema. Large generated
  output is measured and tracked, but it is not a blocker for adopting this
  route.

The intended dependency flow is:

```text
trait -> Package.swift trait-conditioned define
      -> plugin reads compilationConditions
      -> active API slice manifests selected and merged
      -> Apple filter/typeOverrides -> Apple generator once
      -> facade availability and compiled symbols change
```

Traits are API-surface and generated-output controls. They control generation
scope and depth, not individual endpoint parameters. Endpoint parameters remain
defined by the official schema and Apple's generated `Operations.*.Input`
types.

The default implementation keeps one plugin on `AppStoreConnectPublicAPI`.
`Package.swift` maps traits to generated compilation conditions such as
`ASC_PUBLIC_API_BASE`, `ASC_PUBLIC_API_COMMERCE`, `ASC_PUBLIC_API_REPORTS`,
and `ASC_PUBLIC_API_FULL`. The plugin reads those conditions and uses them to
choose slice manifests. `PublicAPIFull` has precedence over narrower domain
slices; when it is enabled, the active run uses the full slice policy rather
than adding redundant domain filters. JSON value replacement is a manifest
policy inside a trait slice, not a different public trait name. Existing facade
method signatures must not change when a trait enables deeper generated
coverage; new typed overlay methods may be added behind the trait.

A separate generated helper target is an implementation detail introduced only
when Apple generated symbol shape, compile cost, or source-size isolation
requires it. Such a helper must not be named as if it were the public API
surface; for example, `PublicAPICommerce` remains the trait/API slice, while
any helper target would use an internal generated-support name.

## Validation

Codegen is complete for a schema snapshot only when:

- the schema provenance file records the exact source snapshot used for
  generation;
- the schema audit file is deterministic for the locked snapshot and records
  the inventory needed to review drift;
- `plan` output is deterministic for the tracked schema and generation inputs;
- `validate` fails on missing provenance, invalid partitions, unsupported
  Apple generation configs, duplicate output paths, and unexpected operation
  count drift;
- generator tests cover representative Apple filter, typeOverrides config,
  trait partition, facade, and selected-client generation cases;
- `swift build` and `swift test` invoke generation without checked-in generated
  Swift output.

Current status: the selected typed-client path is active for the current public
workflow seed.
Its tracked `openapi-capabilities.json` drives `openapi.json`, which contains 7
capabilities, 74 paths, 128 operations, and 240 referenced component schemas.
Default
`swift build` verifies the selection stamp and compiles the typed generated
source emitted by `AppStoreConnectOpenAPIGen` through its host tools:

- `Types.swift`: 93,690 generated lines;
- `Client.swift`: 26,040 generated lines;
- `AppStoreConnectPublicAPI+Facade.swift`: 1,494 generated lines;
- generated `Client` async methods for the current apps/release metadata,
  builds, TestFlight, media assets, reports, users, and certificates/profiles
  core operation slice.
- generated `AppStoreConnectPublicClient` capability subclients and 128
  capability method wrappers over the selected operations.

Measured Apple generation sizes from the locked schema:

- selected deep `types + client`: 119,730 generated lines, about 6.2 MB;
- selected `client` only: 26,040 generated lines, about 1.2 MB, but it is not
  standalone because it depends on `Types.swift`;
- full deep `types + client`: 916,788 generated lines, about 48 MB;
- full shallow `types + client` with all component schemas overridden to
  `OpenAPIRuntime.OpenAPIValueContainer`: 792,546 generated lines, about 40 MB.
  This measurement proves that `Operations.*`, `Input`, `Output`,
  `APIProtocol`, and `Client` remain significant even when component schemas
  are replaced. The first trait-aligned route accepts that generated output can
  be large and keeps size optimization as follow-up work.

## Risks / Known Gaps

- Full shallow Apple generation is still large because `Operations.*`,
  `Input`, `Output`, `APIProtocol`, and `Client` methods remain generated for
  every operation even when component schemas are type-overridden.
- Generated capability facades currently normalize common operation suffixes
  into resource methods and pass through generated input/output types; deeper
  product-level convenience APIs remain handwritten on top of that generated
  base.
- The selected typed-client lane is intentionally allowlisted. Broad endpoint
  coverage expands by adding trait-aligned Apple filters and reviewing generated
  source size and compile profile.
- The Apple-only first route has no package-owned full lightweight raw catalog.
  If CLI or SDK capability coverage needs full low-cost raw reachability without enabling a
  large Apple generated lane, a package-owned catalog emitter can be added
  later as a measured exception.
- Public API codegen does not cover Iris or WebSession behavior.
